> 写给：林晓研（组件库负责人）
> 读者基础：已注册 GitHub、会用分支和提交推送，但没发过 Pull Request；用 vibecoding 让 AI 辅助写代码
> 目标：学完这份教程后，你能用 AI 辅助把 HTML 设计稿变成团队所有人都能直接使用的组件，并用 PR 流程合并到主分支

## 这份教程会教你什么

读完整份教程，你会掌握四件事：

1. 认识组件库仓库的结构，知道每个目录放什么
2. 在本地启动预览环境，实时看到组件效果

4. 用 Pull Request（简称 PR）流程把做好的组件合并到主分支，让团队用上

教程按顺序读就行。遇到不懂的地方，跳到最后一章「遇到问题怎么办」。

## 第一部分 认识组件库仓库

### 1.1 仓库是做什么的

组件库是一个独立的 Git 仓库，存放 App 前端和网页前端共用的组件与设计规范。你在 HTML 设计稿里定义的视觉样式，会在这里变成一个个 `.vue` 组件文件。团队成员做页面时，先来这里找现成组件用，不用每次手写样式。

### 1.2 目录结构

仓库由组长尹辰已经初始化好，结构如下：

```
aistock-component-lib/
├── src/
│   ├── components/        # 你写的组件都放这里（每个 .vue 文件是一个组件）
│   ├── styles/
│   │   └── variables.scss # Design Token 设计变量（颜色、字号、间距等）
│   └── index.ts           # 统一导出入口（做完的组件在这里登记）
├── dev/                   # 本地预览环境
│   ├── App.vue            # 预览页面（引入组件看效果）
│   ├── main.ts            # 预览环境入口
│   └── global.scss        # 预览环境基础样式
├── design/                # 你的 HTML 设计稿放这里
├── docs/
│   └── 组件库搭建教程.md   # 本教程
├── AGENTS.md              # AI 开发助手调用指引（让 AI 读的规则文件）
├── package.json           # 项目配置和依赖清单
├── vite.config.ts         # 预览环境配置
├── tsconfig.json          # TypeScript 配置
└── README.md              # 仓库说明
```

你主要在三个地方工作：

- `src/components/` — 写组件的地方，这是你的核心工作区
- `src/index.ts` — 每做完一个组件，在这里登记导出
- `dev/App.vue` — 想看组件效果时，在这里引入组件预览

`AGENTS.md` 是给 AI 助手读的规则文件，里面写明了组件库的标签规范、命名规范、Design Token 用法等约束。你让 AI 生成组件时，AI 会自动读这个文件，按规则生成。

### 1.3 技术栈说明

| 技术 | 作用 | 你需要了解的程度 |
|------|------|----------------|
| Vue 3 | 组件框架，每个组件是一个 `.vue` 文件 | 让 AI 写，你验收效果 |
| TypeScript | 给代码加类型标注 | 让 AI 写，你不用管 |
| SCSS | 样式预处理器，支持变量和嵌套 | 让 AI 写，你验收效果 |
| rpx | uni-app 的尺寸单位，自动适配不同屏幕 | 知道用 rpx 不用 px 即可 |
| Vite | 本地预览工具，启动后能实时看组件效果 | 会用命令启动即可 |

### 1.4 组件库和前端项目的关系

组件库本身不是 App，它只提供组件文件。App 前端项目（`aistock-app-frontend`，基于 uni-app）会引用组件库里的 `.vue` 文件，在自己的页面里使用。

因为 App 前端用 uni-app 框架，组件必须按 uni-app 规范写：用 `view`/`text` 标签（不用 `div`/`span`）、用 `rpx` 单位（不用 `px`）。这些约束已经写在 `AGENTS.md` 里，AI 生成时会遵守。本地预览环境会自动把这些 uni-app 规范转换成浏览器能识别的格式，让你不用装完整的 uni-app 工具链就能看到效果。

## 第二部分 本地环境搭建与预览

### 2.1 安装 Node.js 和 pnpm

如果电脑上还没装 Node.js，打开浏览器访问 `https://nodejs.org`，下载 **LTS 版本**，双击安装，一路下一步。

装完后按 `Win + R`，输入 `cmd` 回车打开命令行，输入 `node -v` 验证。显示版本号就说明装好了。

接着装 pnpm（包管理工具），在命令行输入：

```
npm install -g pnpm
```

装完输入 `pnpm -v` 验证。

### 2.2 安装 VS Code 和插件

VS Code 是写代码的编辑器，也是 vibecoding 的主战场。访问 `https://code.visualstudio.com` 下载安装。

装完打开 VS Code，点左侧扩展图标（四个方块），搜索并安装：

- **Vue - Official**（Vue 官方插件，写 Vue 代码必备）
- **SCSS Formatter**（格式化 SCSS 样式）

### 2.3 克隆仓库并安装依赖

用你顺手的 Git 工具把组件库仓库克隆到本地。建议克隆到 `D:\aistock\aistock-component-lib`，和前端项目放一起。

克隆完后，用 VS Code 打开这个文件夹（`File` → `Open Folder`）。在 VS Code 里打开终端（顶部菜单 **Terminal** → **New Terminal**），输入：

```
pnpm install
```

这一步会下载项目需要的所有第三方库，可能要等一两分钟。看到最后一行没有红色报错就说明成功了。

### 2.4 启动本地预览

在终端里输入：

```
pnpm dev
```

终端会显示一个本地网址（类似 `http://localhost:5173`），按住 Ctrl 点击它，浏览器会打开预览页面。

这个页面就是 `dev/App.vue`。以后你想看某个组件的效果，就在 `dev/App.vue` 里引入它，保存后浏览器会自动刷新显示最新效果。

> 预览环境开着的时候不要关闭终端窗口。关了终端预览就停了。要停止预览，在终端里按 `Ctrl + C`。

## 第三部分 Design Token 设计规范

Design Token 是一套统一的样式变量（颜色、字号、间距、圆角、阴影等）。所有组件的样式值都必须用这些变量，不能写死具体数值。这样做的好处是：以后想调整全局风格，只改变量就行，不用一个个组件改。

### 3.1 设计稿是唯一参照

你的 HTML 设计文件（放在 `design/` 目录下）里已经定义了完整的设计规范——颜色、字号、间距、圆角、阴影都有。**那份设计稿是组件库视觉规范的唯一参照**，写组件时对照设计稿取值就行。

仓库里的 `src/styles/variables.scss` 是 Design Token 的代码落地，里面的变量名和设计稿一一对应。你不需要背变量表，让 AI 写组件时，AI 会自动读 `AGENTS.md` 和这个变量文件，对照设计稿找对应变量名。

### 3.2 在组件里怎么用变量

预览环境已经全局引入了变量文件，组件的 `<style>` 里可以直接用变量名，不用手动 import：

```scss
<style lang="scss" scoped>
.my-card {
  background: $bg-color-grey;      // 对照设计稿的卡片背景色
  border-radius: $radius-base;     // 对照设计稿的圆角
  padding: $spacing-base;          // 对照设计稿的间距
  box-shadow: $shadow-card;        // 对照设计稿的阴影
}
</style>
```

核心规则：**设计稿里用到的每一个样式值，都去 `variables.scss` 里找对应变量名，用变量，不写死**。如果设计稿里出现了 `variables.scss` 还没有的值，告诉尹辰，他会在变量文件里补上。

### 3.3 A 股涨跌色特别提醒

A 股是「红涨绿跌」，和欧美相反。涉及股票涨跌展示的组件，上涨用红色变量 `$stock-up-color`，下跌用绿色变量 `$stock-down-color`，不要搞反。这条约束也写在 `AGENTS.md` 里，AI 生成时会遵守。

## 第四部分 用 AI 生成组件

你用 vibecoding 让 AI 写组件，核心是**把设计稿和约束讲清楚**，让 AI 产出符合规范的组件。这一部分讲怎么给 AI 下指令、怎么验收产出。

### 4.1 把 HTML 设计稿放进仓库

把你做好的 HTML 设计文件放到仓库的 `design/` 目录下（比如 `design/design-system.html`），提交并推送到 GitHub（参考第六部分的 PR 流程）。

这样团队成员也能看到你的设计稿，AI 生成组件时也能直接读取这个文件作为参照。

### 4.2 给 AI 下指令的要点

每做一个组件，给 AI 的指令要包含三要素：

1. **参照哪个设计稿**：告诉 AI 去读 `design/` 下的哪个 HTML 文件，照着哪个视觉模块做
2. **组件叫什么、做什么用**：比如「做一个 Card 卡片组件，用于页面内容容器，支持标题和副标题」
3. **可配置项（Props）有哪些**：哪些内容是用的人传进来的（比如标题文字、按钮类型），哪些是固定的

指令示例：

> 帮我在 `src/components/Card.vue` 做一个卡片组件。参照 `design/design-system.html` 里的卡片样式。组件支持 Props：`title`（标题文字）、`subtitle`（副标题）。卡片内容用 slot 占位，让用的人自己放。遵守 AGENTS.md 里的规范。

AI 会读 `AGENTS.md` 里的规则（标签用 `view`/`text`、单位用 `rpx`、类名加 `as-` 前缀、样式用 Design Token 变量），生成符合规范的 `.vue` 文件。

### 4.3 验收 AI 的产出

AI 生成组件后，你要检查这几件事：

1. **预览效果对不对**：在 `dev/App.vue` 里引入组件，启动预览，看显示效果和设计稿是否一致
2. **标签有没有用对**：打开生成的 `.vue` 文件，确认 `<template>` 里用的是 `view`/`text`，不是 `div`/`span`（如果用错了，让 AI 改）
3. **样式有没有用变量**：确认 `<style>` 里用的是 `$brand-color` 这样的变量，不是写死的 `#4d7cfe`（写死了让 AI 改）
4. **有没有用 emoji**：图标应该用 `SvgIcon` 组件，不能出现 emoji 表情（出现了让 AI 改）

验收不满意就继续跟 AI 对话调整，直到效果和设计稿一致。

### 4.4 登记导出组件

验收满意后，在 `src/index.ts` 里登记这个组件，让团队能统一引用：

```ts
export { default as Card } from './components/Card.vue'
```

每做完一个组件，都在这里加一行导出。这一步也可以让 AI 帮你加。

### 4.5 组件骨架参考

如果你想知道 AI 生成的组件大概长什么样，这是一个典型的组件结构。你不用手写，了解结构便于验收：

```vue
<template>
  <!-- 用 view/text 标签，不用 div/span -->
  <view class="as-组件名">
    <text class="as-组件名-标题">{{ title }}</text>
    <view class="as-组件名-内容">
      <slot />  <!-- 内容占位符，用的人在这里放内容 -->
    </view>
  </view>
</template>

<script setup lang="ts">
// Props 定义，用 withDefaults 写法
withDefaults(defineProps<{
  title?: string
}>(), {
  title: ''
})
</script>

<style lang="scss" scoped>
/* 用 Design Token 变量，不写死颜色和尺寸 */
.as-组件名 {
  background: $bg-color-grey;
  border-radius: $radius-base;
  padding: $spacing-base;
}
</style>
```

关键验收点：`<template>` 用 `view`/`text`、`<script setup lang="ts">`、`<style lang="scss" scoped>`、类名 `as-` 前缀、样式用变量。这几点都对，组件就基本合格。

## 第五部分 组件开发规范

这一部分的规范已经写在 `AGENTS.md` 里，AI 生成时会遵守。你了解这些规范，便于验收 AI 的产出。

### 5.1 命名规范

| 对象 | 规范 | 示例 |
|------|------|------|
| 组件文件名 | 大驼峰，一个组件一个文件 | `Card.vue`、`EmptyState.vue` |
| 组件类名 | 统一 `as-` 前缀 + 短横线连接 | `as-card`、`as-btn--primary` |
| Props 名 | 小驼峰 | `title`、`showHeader` |
| 事件名 | 小写连字符 | `@click`、`@change` |

### 5.2 标签规范

组件要被 uni-app 项目使用，必须用以下标签，不能用 HTML 原生标签：

| 用途 | 用这个 | 不要用 |
|------|--------|--------|
| 容器/区块 | `<view>` | `<div>` |
| 文字 | `<text>` | `<span>` / `<p>` |
| 图片 | `<image>` | `<img>` |
| 滚动区域 | `<scroll-view>` | 自己写 overflow |

### 5.3 样式规范

- `<style lang="scss" scoped>` 必须加 `scoped`，防止样式污染别的组件
- 所有颜色用 Design Token 变量，不写死
- 所有尺寸用 rpx，不用 px
- 嵌套写法用 SCSS 的 `&` 语法

### 5.4 图标规范

项目里禁用 emoji 表情符号，所有图标用 `SvgIcon` 组件加载 SVG 文件。SVG 图标文件放在 `src/static/assets/icons/` 下，命名用短横线（如 `bell-line.svg`）。

## 第六部分 GitHub 协作与 PR 流程

组件库采用 Pull Request（PR）流程：你在自己的分支上开发组件，开发完后发一个 PR 请求，尹辰检查通过后合并到主分支 `main`。这样能保证主分支始终是稳定可用的状态。

这一部分是你需要自己操作的（不能靠 AI），要熟悉。

### 6.1 开工前：拉取最新代码

每次开始工作前，先切到 `main` 分支，拉取最新代码：

```
git checkout main
git pull
```

用 GitHub Desktop 的话：左上角选 `main` 分支，点 **Fetch origin**，有更新就点 **Pull origin**。

### 6.2 创建开发分支

不要在 `main` 上直接改。为每个组件新建一个分支，分支名用 `feat/组件名` 格式：

```
git checkout -b feat/card
```

> 分支名规范：`feat/组件名`（新增组件）、`fix/组件名`（修复组件问题）、`docs/说明`（改文档）。用英文小写，单词之间用短横线。

### 6.3 开发并提交

在分支上用 AI 生成组件代码（参考第四部分）。写完后提交：

```
git add src/components/Card.vue
git commit -m "feat: 新增 Card 卡片组件"
```

> 提交信息规范：开头用 `feat:`（新增）、`fix:`（修复）、`docs:`（文档）、`style:`（样式调整），后面一句话说清楚改了什么。

> 用 `git add 具体文件路径`，不要用 `git add .` 一次性加所有文件，避免误提交无关改动。

### 6.4 推送分支到 GitHub

```
git push -u origin feat/card
```

第一次推送这个分支时要加 `-u origin`，以后再推送只需 `git push`。用 GitHub Desktop 的话点顶部的 **Push origin** 按钮即可。

### 6.5 在 GitHub 网页发起 Pull Request

这是 PR 流程的关键一步。推送完成后，打开浏览器访问组件库的 GitHub 仓库页面。

1. 仓库页面顶部会出现一条黄色提示「`feat/card` had recent pushes」，点右边的 **Compare & pull request** 按钮
2. 如果没出现这条提示，点页面上方的 **Pull requests** 标签 → 点绿色 **New pull request** 按钮 → 在「compare」下拉框里选你的分支 `feat/card`
3. 进入 PR 创建页面后，填写：
   - **标题**：一句话说明做了什么，比如「feat: 新增 Card 卡片组件」
   - **描述**：简单说明这个组件的作用、改了哪些文件。如果是新增组件，可以贴一张预览截图
4. 确认右边的目标分支是 `main`（base: main ← compare: feat/card）
5. 点绿色的 **Create pull request** 按钮

PR 创建成功后，页面会显示这个 PR 的状态。这时候等尹辰来检查（review）。

### 6.6 等待 review 并处理反馈

尹辰检查你的 PR 后，可能会有几种情况：

**情况一：直接通过合并**
尹辰点 **Merge pull request** 按钮，PR 合并到 `main`。你会收到 GitHub 的邮件通知。合并完成后，这个分支的工作就完成了。

**情况二：提出修改意见**
尹辰会在 PR 页面的「Files changed」里给某些代码行留评论，提出修改建议。你会收到邮件通知。这时：

1. 回到本地 VS Code，切到你的开发分支 `feat/card`
2. 根据评论让 AI 修改代码
3. 提交并推送（`git add` → `git commit` → `git push`）
4. 推送后 PR 页面会自动更新，显示你的新改动，尹辰会继续看

**情况三：有冲突**
如果尹辰在 `main` 上改了和你冲突的文件，GitHub 页面会显示「This branch has conflicts that must be resolved」。这时：

1. 在本地切到 `main`，拉取最新：`git checkout main` → `git pull`
2. 切回你的分支：`git checkout feat/card`
3. 合并 main：`git merge main`
4. 如果有冲突，让 AI 帮你解决（把冲突文件给 AI 看，让它选保留哪些内容）
5. 解决完冲突后，提交并推送：`git add .` → `git commit` → `git push`
6. PR 页面的冲突提示会自动消失

如果冲突不知道怎么解决，截图发给尹辰，不要瞎选。

### 6.7 合并后：清理本地分支

PR 合并完成后，你的开发分支就没用了，可以删掉：

```
git checkout main
git pull
git branch -d feat/card
```

远程分支会在合并 PR 时自动提示删除，点一下就行。

### 6.8 整个流程速查

```
1. git checkout main && git pull        # 拉最新
2. git checkout -b feat/card            # 建分支
3. 让 AI 生成组件代码
4. git add src/components/Card.vue      # 暂存
5. git commit -m "feat: 新增 Card 组件"  # 提交
6. git push -u origin feat/card         # 推送
7. GitHub 网页发 PR                     # 发起合并请求
8. 等尹辰 review                        # 等检查
9. 合并后 git checkout main && git pull && git branch -d feat/card  # 清理
```

## 第七部分 组件清单

### 7.1 基础组件（参考已有实现）

这些组件在 App 前端项目里已经有实现，你可以让 AI 参照它们的写法迁移到组件库。参照路径：`aistock-app-frontend/src/shared/components/`。

| 组件 | 作用 | 关键 Props |
|------|------|-----------|
| `Card` | 卡片容器 | `title`、`subtitle` |

| `EmptyState` | 空状态占位 | `icon`、`text` |
| `LoadingState` | 加载中占位 | `text` |
| `Avatar` | 头像 | `src`、`size` |

### 7.2 业务组件（根据设计稿开发）

这些是根据产品需要待开发的业务组件，以你的 HTML 设计稿为准：

| 组件 | 作用 | 备注 |
|------|------|------|
| `PageCard` | 页面级卡片容器 | 含动态底部高度计算 |
| `SubPageCard` | 子页面卡片容器 | 含返回按钮、滚动区、聊天栏 |
| `StockPrice` | 股票价格展示 | 含涨跌色、涨跌幅 |
| `Tag` | 标签 | 如「预判信号」「重大」标签 |
| `StatCard` | 统计数据卡片 | 数字 + 标签 |
| `ListCell` | 列表行 | 左标题右内容 |

> 具体要做哪些组件，以你的 HTML 设计稿为准。设计稿里出现的每个可复用视觉模块，都做成一个组件。

## 第八部分 常见问题

### 8.1 改了组件但预览页面没变化

检查三件事：是不是忘了保存文件（`Ctrl + S`）、`dev/App.vue` 里是不是正确 import 了组件、终端里的预览进程是不是还开着（关了就 `pnpm dev` 重新启动）。

### 8.2 AI 生成的组件标签用错了（用了 div/span）

直接跟 AI 说「按照 AGENTS.md 的规范，标签用 view/text，不用 div/span，改一下」，AI 会改。

### 8.3 AI 生成的样式写死了颜色

跟 AI 说「按照 AGENTS.md 的规范，样式值用 variables.scss 里的 Design Token 变量，不要写死颜色」，AI 会改。

### 8.4 推送时报错「冲突」

参考第 6.6 节「情况三」处理。冲突可以让 AI 帮你解决，不确定就截图发给尹辰。

### 8.5 发 PR 时找不到自己的分支

确认你已经把分支推送到 GitHub 了（`git push`）。用 GitHub Desktop 的话，确认点过 **Push origin** 按钮。推送后刷新 GitHub 仓库页面再试。

### 8.6 pnpm install 报错

可能是网络问题。试试切换 pnpm 镜像源：

```
pnpm config set registry https://registry.npmmirror.com
```

再重新 `pnpm install`。还不行就截图发给尹辰。

## 第九部分 遇到问题怎么办

1. **先看这份教程**——特别是第六部分的 PR 流程速查
2. **先问 AI**——代码层面的问题（标签、样式、组件写法）直接让 AI 解决
3. **截图发给尹辰**——Git 操作、PR 流程、冲突解决这类操作问题，截图发飞书给尹辰
4. **不要自己瞎猜**——Git 冲突、PR 合并这种不可逆的操作，不确定就先问

你的核心任务是「把控设计稿到组件的转化质量」：让 AI 按规范生成，你验收效果和规范符合度，用 PR 流程合并。组长会全程指导你，有问题随时问。
